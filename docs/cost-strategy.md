# ssyung 비용 절감 전략

> 상태: 초안 (2026-10-17)
> 관련 문서: [architecture.md](architecture.md)

## 0. 요약

- **초기 손익을 좌우하는 것은 AI가 아니라 서버 고정비다.** 고정비는 모델 선택과 무관하므로 호스팅 구성으로 줄인다.
- 웹을 Vercel 대신 Cloud Run에 올려 고정비를 **월 8만~11만 원에서 월 약 4.6만 원**으로 낮춘다. 연 10만 원 이용권 기준 손익분기는 학교 12~13곳에서 **약 6곳**으로 줄어든다.
- AI는 **Haiku 4.5를 기본 모델**로 시작한다. 단순한 명령만 처리하고 날짜·교시 계산은 서버가 미리 하므로 충분할 가능성이 높다. 검증에 실패한 요청만 Sonnet 5.5로 다시 보낸다.
- AI 호출은 1회 약 10원, 학교 1곳당 연 약 1.3만 원(보통 사용량)이다.

## 1. 비용 구조

### 1.1 AI 호출 1회

가정: 입력 약 5천 토큰(지시문·출력 스키마 1.5천 + 학교 정보 3천 + 요청 문장), 출력은 추론 포함 약 1천 토큰(추론 강도를 낮추거나 추론을 쓰지 않으면 약 300토큰). 가격은 2026-10 기준 Anthropic API 정가, 환율 1달러 = 1,400원 가정.

| 모델 | 입력 / 출력 (100만 토큰당) | 1회 비용 |
|---|---|---|
| **Claude Haiku 4.5 (기본)** (출력 약 300토큰) | $1 / $5 | 약 $0.0065 (9원) |
| Claude Sonnet 5.5, effort `low` (출력 약 300토큰) — 재시도용 | $2 / $10 | 약 $0.013 (18원) |
| Claude Sonnet 5.5 (출력 약 1천 토큰) | 〃 | 약 $0.02 (28원) |
| Claude Opus 5.5 (출력 약 1천 토큰) | $4 / $20 | 약 $0.04 (56원) |

### 1.2 학교 1곳당 연간 AI 비용

**호출 수 가정의 근거** (실측 전 추정)

| 사용량 | 변경 요청 | 계산 | 월 호출 |
|---|---|---|---|
| 적음 | 하루 약 1건 | 20건 × 1.5 | 30 |
| 보통 | 하루 2~3건 | 수업일 약 20일 × 2.5건 = 50건 × 1.5 | 75 |
| 많음 | 하루 6~7건 | 약 130건 × 1.5 | 200 |

- 1.5배는 해석이 틀려 다시 입력하는 경우와 상위 모델 재시도를 포함한 여유분이다.
- **이 숫자는 가정이다.** 특수교사 팀원에게 "일정 변경이 일주일에 몇 번 생기는지"를 확인해 갱신하고, 파일럿에서 실측값(§4)으로 교체한다.

| 사용량 | 월 호출 | **Haiku 4.5** | Sonnet 5.5 | Opus 5.5 |
|---|---|---|---|---|
| 적음 | 30 | **약 0.5만 원** | 약 1만 원 | 약 2만 원 |
| 보통 | 75 | **약 1.3만 원** | 약 2.5만 원 | 약 5만 원 |
| 많음 | 200 | **약 3.4만 원** | 약 6.7만 원 | 약 13만 원 |

학교 10곳, 보통 사용량이면 Haiku와 Sonnet의 차이는 연 약 12만 원이다. 고정비(§1.3)를 줄이는 효과가 더 크다.

### 1.3 고정비

아래 금액과 플랜 조건은 기억에 의존한 **추정치이며 계약 전 확인이 필요하다.**

**기존안 (Vercel 사용)**: 월 8만~11만 원, 연 100만~130만 원

**변경안 (웹도 Cloud Run)**

| 항목 | 월 비용 (추정) | 비고 |
|---|---|---|
| Supabase Pro | 약 $25 | 자동 백업, 서울 리전. 실제 학교 데이터를 받기 전 필수 |
| 웹 + Solver (Cloud Run) | 0 ~ 수 달러 | 사용량 과금. 이 규모에서는 무료 사용량 안에 들어올 가능성이 큼 |
| Apple 개발자 등록 | 연 $99 (월 약 $8) | 앱 배포에 필요 |
| Google Play 등록 | 1회 $25 | |
| Expo (EAS) | 무료 플랜 | 빌드가 많아지면 유료 검토 |
| SMS | 건당 수십 원 | 앱 푸시가 기본, SMS는 대체 발송분만 (변동비) |
| **합계** | **월 약 $33 (약 4.6만 원)** | 연 약 55만 원 |

Vercel을 빼는 이유:
- 월 $20 × 인원이 줄어든다.
- Vercel 무료 플랜은 상업적 이용이 금지된 것으로 알고 있어 유료 서비스에는 쓸 수 없다(확인 필요).
- 솔버와 같은 Google Cloud에 두면 처리위탁·국외이전 고지 대상 사업자가 하나 줄어든다.

포기하는 것: 브랜치별 미리보기 배포, 설정 없는 배포. GitHub Actions로 Cloud Run 배포를 자동화해 보완한다.

DB를 직접 서버에 설치해 운영하면 더 싸지만, 백업과 보안을 직접 책임져야 한다. 학생 데이터를 다루므로 하지 않는다.

## 2. 절감 전략

효과가 큰 순서로 정리했다.

### 2.1 고정비: 호스팅 구성 (§1.3)

- 웹과 솔버를 모두 Cloud Run에 두고 사용한 만큼만 낸다.
- **파일럿 준비 기간**(실제 학교 데이터 없이 코드 데이터로 개발·시연하는 기간)에는 Supabase도 무료 플랜을 쓴다. 무료 플랜은 자동 백업이 없고, 오래 쓰지 않으면 일시 정지되는 것으로 알고 있다(확인 필요).
- **실제 학교 데이터를 받기 직전**에 Supabase Pro로 전환한다.

### 2.2 AI는 해석만 한다 (적용됨)

시간표 계산은 솔버가 하고, AI는 변경 요청을 변경 명령(JSON)으로 바꾸기만 한다. AI가 시간표 전체를 출력하는 구조였다면 출력이 1만~2만 토큰이 되어 비용이 10배 이상이다. 이 구조는 바꾸지 않는다.

### 2.3 어려운 계산은 서버가 미리 한다

저렴한 모델이 틀리기 쉬운 부분은 명령의 복잡도가 아니라, 문장 속 표현을 실제 데이터에 연결하는 일이다. 이 부분을 서버가 미리 계산해 넘기면 모델은 주어진 값 중에서 고르기만 하면 된다. **Haiku를 기본 모델로 쓸 수 있는 전제 조건이다.**

| 모델이 직접 하면 틀리기 쉬운 것 | 서버가 미리 넘기는 값 |
|---|---|
| "내일", "다음 주 수요일" | 오늘 날짜, 이번 주·다음 주 달력 |
| "오전", "점심 이후" | 학교 규칙 (예: 오전 = 1~4교시) |
| "3반 체육 시간" | 반별 과목 → 교시 대응표 |
| 존재하지 않는 코드 | 사용 가능한 코드·장소 목록 (enum으로 스키마에 넣음) |

### 2.4 Haiku 기본, 실패 시 Sonnet

```
요청 ─▶ Haiku 4.5 해석 ─▶ 서버 검증 ─┬ 통과 ──────────────────▶ 교사 확인 카드
                                     └ 실패 / confidence 낮음 / unsupported
                                         ─▶ Sonnet 5.5 (effort low) 재해석 ─▶ 교사 확인 카드
```

- **기본 모델은 Haiku 4.5로 정한다.** 처리할 명령이 단순하고, §2.3으로 어려운 부분을 서버가 맡기 때문이다.
- 출력 스키마에 `confidence`와 `unsupported`를 둔다. 확신이 낮거나 표현할 수 없는 요청이면 억지로 맞추지 말고 그렇게 표시하도록 지시한다.
- 서버 검증 항목: 코드가 실제로 있는지, 교시 범위가 맞는지, 명령끼리 충돌하지 않는지.
- 대부분의 요청이 Haiku에서 끝나므로 평균 비용은 Haiku에 가깝다.
- 확정 전에 §3 평가 세트로 Haiku 정확도를 한 번 확인한다. 목표에 크게 못 미치면 Sonnet 기본으로 되돌린다.

### 2.5 학교 정보를 필요한 만큼만 보낸다

원반 시간표 전체 대신, 요청에 언급된 반·요일·지원인력 주변 정보만 보낸다. 입력이 절반 이하로 줄어든다. 단, 너무 줄이면 정확도가 떨어지므로 평가 세트로 확인한다.

### 2.6 프롬프트 캐싱은 기대하지 않는다

- Haiku 4.5는 4,096토큰보다 짧은 프롬프트 앞부분은 캐싱하지 않는다. 공용 지시문과 스키마가 약 1.5천 토큰이라 캐싱 대상이 아니다.
- 기본 캐시는 5분간 유지되는데, 교사 요청은 보통 그보다 간격이 길다.
- 그래도 공용 지시문과 스키마를 맨 앞에 고정하고, 날짜처럼 매번 바뀌는 값은 그 뒤에 넣는 순서는 지킨다. 재시도용 Sonnet이나 이후 다른 모델에서 캐싱이 가능해질 때 바로 효과를 본다.

### 2.7 학교별 월 호출 상한

예: 월 300회. 상한에 가까워지면 교사에게 안내하고 그리드에서 직접 수정하도록 유도한다. 비정상 사용에도 비용을 예측할 수 있다.

### 2.8 알림은 푸시 우선

앱 푸시는 무료다. SMS는 앱을 설치하지 않았거나 일정 시간 안에 확인하지 않은 경우에만 보낸다.

## 3. 모델 확인 절차

1. **평가 세트 작성**: 특수교사 팀원과 실제로 나올 법한 요청 문장 50~100개와 정답 변경 명령을 만든다. 실명 없이 코드로만 쓴다. §2.3의 어려운 유형(날짜, 오전·오후, 과목 → 교시, 복합 명령, 지원하지 않는 요청)을 골고루 넣는다.
2. **비교 실행**: Haiku 4.5와 Sonnet 5.5(effort `low`)에 같은 세트를 돌린다. 비용은 모델당 몇 달러 수준이다.
3. **판단 기준** (목표 정확도는 파일럿 전에 확정, 예: 95%):
   - Haiku 단독으로 목표 이상 → Haiku 단독
   - Haiku + Sonnet 재시도 구조로 목표 이상 → §2.4 구조 유지
   - 둘 다 미달 → Sonnet 기본
4. **재평가**: 프롬프트, 스키마, 모델 버전을 바꿀 때마다 같은 세트로 다시 돌린다.

`unsupported`를 정확히 판정하는지는 별도로 본다. 틀린 JSON을 그럴듯하게 만드는 것이 가장 위험한 실패다. 교사가 확인 카드를 자세히 읽지 않고 누를 수 있으므로, 확인 단계만 믿고 정확도 기준을 낮추지 않는다.

## 4. 측정

호출마다 아래를 기록한다. 요청 원문과 응답 원문은 저장하지 않는다(실명 금지 원칙, architecture.md §5.5).

| 필드 | 용도 |
|---|---|
| `school_id`, `change_request_id` | 학교별 사용량 |
| `model`, `effort` | 모델별 비용 |
| `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` | 실제 비용 계산, 캐시 효과 확인 |
| `escalated` | Sonnet 재시도 여부 |
| `teacher_edited` | 교사가 확인 카드에서 고쳤는지 (실제 정확도) |

대시보드 지표:
- 학교별 월 호출 수와 비용 (§1.2 가정 검증)
- 요청 1건당 평균 비용
- Sonnet 재시도 비율
- 교사 수정 비율

## 5. 가격 정책에 주는 시사점

변경안 고정비(연 약 55만 원) + Haiku 기준(보통 사용량, 학교당 연 약 1.3만 원):

| 이용권 (연) | 학교당 AI 비용 비중 | 손익분기 |
|---|---|---|
| 10만 원 | 약 13% | 약 6곳 |
| 20만 원 | 약 7% | 약 3곳 |
| 30만 원 | 약 4% | 약 2곳 |

인건비, 결제 수수료, SMS, 부가세는 빠져 있다. 파일럿 측정값(§4)으로 다시 계산한 뒤 가격을 정한다.

## 6. 다시 볼 시점

- 특수교사 팀원 확인 후: §1.2 호출 수 가정 갱신
- 파일럿 1주차 측정값이 나왔을 때: §1 추정치를 실측값으로 교체
- 교사 수정 비율이 목표보다 높을 때: §2.3 사전 계산 보강, 그래도 안 되면 Sonnet 기본으로 전환
- Sonnet 재시도 비율이 30%를 넘을 때: Sonnet 단독이 더 싼지 계산
- 학교 수가 늘어 Cloud Run 무료 사용량을 넘을 때: 호스팅 비용 재계산
- 새 모델이 나오거나 가격이 바뀔 때: §3 평가 재실행
